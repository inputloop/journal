## What CSDW is

**CSDW** — *"dictionary to format, repeatedly, reusably."* A runtime system that reads dictionary sources (TSV, JSON, plaintext, or user-defined formats) and outputs them in multiple formats (TSV, HTML, Markdown, JSON, JSONL, or template-driven custom). It grows projects, manages multiple dictionaries, and can scaffold agents for users who need them.

## The moving parts, in order a cold reader needs them

1. **Dictionary source** — the unit of work. User-supplied (a file path, a URL, context-inferred from project) or generated by an agent. CSDW reads it, validates it, stores it in the project.

2. **Project structure** — optional but central:
   ```
   my-dict-project/
     ├─ data/                # dictionaries live here
     │  ├─ main.tsv
     │  └─ secondary.json
     ├─ templates/           # optional format templates
     ├─ outputs/             # generated files
     ├─ .csdwrc              # overrides and config
     └─ agent/               # optional AI agent setup
   ```

3. **Format transformers** — one per output format (tsv, html, json, markdown, jsonl, custom). Each is composable; the tool chains them (e.g., read TSV → transform to HTML → apply template → write).

4. **Agent (optional):** If user-configured, handles:
   - Adding columns (e.g., translations, definitions, examples)
   - Reformatting dictionaries
   - Integrating external data
   - Publishing outputs
   - Answering questions about the dictionary

5. **Prove-a-promise pattern:** Every transform proves it kept its promise via two tests:
   - **Universal:** round-trip identity (read → transform → read back = original)
   - **Format-specific:** (e.g., HTML validates, JSON parses, TSV round-trips without data loss)

## Core doctrine (what survives the tests)

- **Reusable, not locked:** GPLv3+; users own their copies, forks, and modifications. No central gate.
- **Self-contained:** Seed defaults make CSDW work out-of-the-box. Overrides (dot-file) let users customize without editing the tool.
- **Self-healing:** Designed for drift and oneshot adaptations. Tool accumulates working patterns.
- **Write surfaces required:** If no place exists to write (save work), tool refuses. No silent failures.
- **Two test paths always:** Behavioral (does output match expected?) + invariant (does it round-trip?). Both must pass.

## How to resume cold

1. Read this file (you're doing it).
2. Check `.csdwrc` or `csdw/.config/` for user overrides.
3. Inspect `data/` for available dictionaries and their formats.
4. Run `csdw.sh --help` to see available commands.
5. For agent-based tasks, see `AGENT-SETUP.md`.

## Standing directives

- **Refuse without a write surface.** If the user hasn't specified where to save output, ask. If they can't provide one, stop.
- **Defend from first principles.** Every feature should be defensible: Does it serve reuse? Does it respect user agency? Can the user modify it?
- **Test round-trip.** Before declaring a transform successful, verify it can be reversed (or at least, that data isn't lost).
- **Let users write.** Whether they edit the tool, the config, or the dictionaries, they should be able to do so freely.
- **Name the format.** When reading a dictionary, identify its format explicitly; don't guess.
- **Handle drift.** Oneshot prompts (to agents) will succeed differently each time. Tool should accumulate learnings, not fight the variation.

## Where things live

- `csdw.sh` — the runtime script (POSIX, standalone)
- `data/` — dictionaries managed by the project
- `templates/` — format templates (HTML, Markdown, etc.)
- `outputs/` — generated files (versioned, never clobbered)
- `.csdwrc` — user config and overrides
- `agent/` — optional AI agent scaffold (see AGENT-SETUP.md)
- `.csdw-manifest` — inventory of dictionaries and their schemas
- `.models/` — archived model snapshots

## What CSDW does NOT do

- Does not require network access (offline-first)
- Does not phone home or track usage
- Does not assume any AI or Corwork context
- Does not control how users modify or distribute their copies
- Does not require signup, authentication, or licensing gates

## The two test paths

**Behavioral:** Does CSDW produce the output the user asked for?
- Format matches request (TSV, HTML, JSON, etc.)
- Data is complete and uncorrupted
- Template (if supplied) was applied correctly

**Invariant:** Can the output be read back without data loss?
- TSV → JSON → TSV round-trips to original
- HTML is valid and parseable
- All columns, all rows, all values survive the journey

Both paths must pass. A transform that passes behavioral but fails invariant is silently corrupted data — unacceptable.
